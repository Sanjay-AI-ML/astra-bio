# ASTRA-BIO — software overview

Status reviewed on 12 October 2026 against the current source, model reports and transport verification records. This review did not rerun the complete historical test suite.

ASTRA-BIO is a working local decision-support prototype for connecting crew dietary targets, stored food, crop harvest schedules and resource budgets. Its React interface calls a real FastAPI backend and Pyomo/HiGHS optimizer. It can save and compare plans, run local plant-image inference and display MongoDB Atlas telemetry. The intended autonomous biological ecosystem remains a broader development goal: physical hardware, automatic feedback/control and biological validation are still incomplete.

**A typical planning flow** starts with reviewed dietary targets, entered food stocks, crop profiles and mission budgets. The optimizer calculates daily aggregate food allocations and future planting/harvest batches. A disruption changes future conditions; the simulator compares keeping the original plan with replanning from the same event-day inventory and active crops. The dashboard displays both outcomes and explicit shortages. Sensor monitoring is a separate live flow and does not automatically change the planning inputs.

| Workspace | Implemented behavior | Practical boundary |
| --- | --- | --- |
| Mission overview | Saved mission-day explorer, event/harvest/first-gap markers, fixed/adaptive policy selection, nutrient/water/electricity charts and related-workflow links | These charts are saved simulation outputs, not measured biological performance |
| Crew & nutrition | Crew profiles, gram-based food intake logs, complete/partial declarations, intake-to-target calculations, reviewed mean targets and local dietary snapshots | Manual targets; only energy, protein and vitamin C; aggregate planner allocations |
| Mission inputs | Crew count, duration, growing area, water/power budgets, reserves, dietary targets, food-mass/upper nutrient limits and planting increments | Entered assumptions require explicit validation/submission |
| Crops & food | Editable crop coefficients, actual solved planting/harvest timelines, stored-food stocks, reserve eligibility, declared expiry and optional nutrient-retention assumptions | Fresh harvest is consumed/discarded on harvest day; cooking, refrigeration and recipes are absent |
| What-if simulator | Nominal, water shortage, crop loss, crew increase and dietary-change starters; water/power factors and event-day edits; real fixed/adaptive solves; daily/whole-run comparisons | Changes are applied explicitly; resource-stress yield behavior remains a labelled simulation proxy |
| Plant screening | Local ONNX inference, tentative/uncertain/rejected results, model-version selection/rollback and screening JSON export | Tomato, potato and bell pepper only; lettuce and most planning crops are unsupported |
| Live devices | Device/source selection, latest values, history, missing measurements, packet age, stale/error states and CSV export | Physical board readings are not yet verified; synthetic tests remain labelled |
| Saved plans | Named configuration snapshots, configuration JSON import/export, successful-run history, restoration without re-solving and complete-run export | Persistent saves are explicit or occur after a successful comparison; navigation retention is not automatic saving of every draft |
| Model settings | Ten terrestrial reference profiles, harvest CSV import, endpoint fitting/holdouts, low/mean/high yield sensitivity, model evidence and a blank trial template | The measured age curve and environmental-response model are not active planner/control models |

The app uses a white/sage layout with the supplied logo, six primary navigation groups, related tabs, a mobile drawer and Ctrl/Cmd K destination search. The primary navigation has no Research page. Model/source details remain in secondary disclosures for review. Search finds pages and actions rather than searching database records. There is no general food/crop catalogue editor; inventory edits the current catalogue, and configuration JSON import provides broader structural input.

**The planning engine performs mathematical optimization.** It is not a trained health model. Its constraints cover food-stock conservation, harvest availability, growing area, entered water/electricity budgets, crew water allowances, reserve targets, optional whole planting increments, food-mass limits and nutrient upper bounds. Unmet dietary/reserve targets remain visible as shortfalls rather than being replaced with a fabricated feasible plan. The adaptive comparison preserves decisions before the disruption. Verified explanations use saved solver facts; optional local Ollama can select those facts, with a deterministic fallback. No Ollama daemon/model is installed or required.

If a reviewed nutrient target changes today, stored food and already available harvests can address current demand. New crop batches can only contribute after their harvest delay. The software respects that chronology. It currently recommends aggregate food quantities and planting schedules, rather than prepared personalized meals.

**The model status has several distinct parts.**

| Component | Current implementation/evidence | Remaining limitation |
| --- | --- | --- |
| Nutrition calculations | Nine USDA food forms; recorded grams converted to energy/protein/vitamin C; missing and incomplete logs distinguished | No biomarker/wearable interpretation, absorption model, complete diet adequacy or clinical deficiency diagnosis; crop composition is a species proxy |
| Planning crop endpoints | Ten EDEN ISS Antarctic/NASA terrestrial cultivar/environment profiles; reported edible harvest mass and harvest age; calibration and sensitivity tooling | A single withheld NASA trial produced 1.0415 kg/m² / 46.94% error; this is weak transfer evidence, not robust general accuracy |
| Separate lettuce growth curve | 540 plant/day records; 12 training plants and 6 held-out plants; measured-age interpolation; held-out MAE 5.72 g/plant | One source growing cycle, no independent held-out cycles, unspecified fresh-mass basis; not edible-harvest accuracy; inactive in planner/control |
| Plant-image classifier | One completed MobileNetV3 classifier fine-tuning run; local selected ONNX candidate; held-out accuracy 28.75% → 41.25% on 80 PlantDoc images | Only 10 of 15 classes tested; low accuracy; safeguards accepted 6 images with 4 correct; no real tray or unknown-image validation |
| Environmental-response fitting | CSV collection template, grouped fitting, holdouts, baseline comparison and environmental-support guards are implemented | Current report has zero real crop-cycle rows; awaiting measurements; inactive in planner/control |

The image training split contained 636 training, 160 validation and 80 test images after duplicate/conflicting-label exclusions. Checkpoint selection and temperature fitting used validation data. These safeguards improve evaluation hygiene but do not demonstrate reliable diagnosis on the actual tray. The candidate's low acceptance coverage and untested classes require further data and validation before any automatic action.

Reference yield data and the growth curve address different measurements. Published aggregate crop means are not expanded into invented independent cycles. Lighting demand is an engineering estimate with explicit assumptions; net makeup water and full HVAC/pump energy are not measured by the reference data. Lux is not calibrated PPFD, a low-water switch is not a water-volume meter, and one measured DC bus is not total habitat energy use.

**The current telemetry architecture** is ESP32-S3 WROOM → Wi-Fi/verified HTTPS → a device-only Python gateway on the laptop's private LAN address, port 8502 → PyMongo/TLS → MongoDB Atlas → FastAPI → React Live devices. Database credentials remain in ignored backend runtime configuration. The firmware receives its device token and the gateway's public CA certificate. Requests are authenticated per device, range/provenance checked and limited to 16 KiB. Unique sample identities and payload comparisons make identical retries idempotent.

The live software test on 12 October passed: a synthetic sample returned HTTP 201, its identical retry returned HTTP 200, Atlas contained exactly one matching record, authenticated gateway health succeeded and the dashboard read the record. The firmware contains no Atlas URI. The report is `docs/MONGODB_VERIFICATION.json`. This is a real database/HTTPS test using generated measurements; no physical ESP32 delivery is claimed.

The new HTTPS firmware compiled for a generic ESP32-S3 DevKitC-1 N8/no-PSRAM profile with placeholder configuration. Its actual sensor initialization/read hooks are empty. The board variant, pins, Wi-Fi details and sensor drivers still require configuration before flashing and measurement checks. It retains one pending packet across restart and retries with bounded backoff. It pauses new sampling while that packet awaits acknowledgement, so a long outage does not produce a complete historical queue.

The older optional transport is ESPHome → Mosquitto/TLS → Node-RED → SQLite telemetry. Thirteen TLS/authentication/topic-permission/delivery checks passed with generated observations. It remains available as an alternative. Configured Atlas telemetry is not merged with that SQLite history, and an Atlas outage does not silently switch the app to SQLite.

Atlas hosts telemetry storage. Mission configurations, saved comparisons and dietary snapshots still use local SQLite. The dashboard and gateway run on the laptop; it must stay awake, and the ESP32 must be able to reach the gateway. The app has no production multiuser sign-in/roles or verified hosted backend. The local dashboard is loopback-bound, while device ingress is LAN-bound. A cloud database alone does not provide always-on hosting for either service.

**The intended automatic ecosystem loop still needs implementation.** Today, dietary targets are entered/reviewed, model assumptions are explicitly applied, scenarios are explicitly solved, photos are uploaded manually and sensor observations are displayed separately. Future work must define how qualified sensor observations update model inputs, when a replan is requested and how a reviewed plan becomes an equipment command. Crop-image results do not currently isolate/remove crops or trigger a solve. Actuation is disabled throughout the current prototype.

| 6 | Expand nutrients, realistic stored/prepared foods, individualized allocation, recipes and preparation/storage resource accounting | A more complete nutrition/food workflow |
| 7 | Add durable hosting/service management, user authentication/roles, backup/restore, operational alerts, offline history and maintenance workflows | A dependable shared product beyond the laptop prototype |
| Longer research | Oxygen/CO₂, waste/nutrient recycling, full habitat biology and spaceflight transfer studies | Evidence for the broader biological operating-system vision |

Clinical deficiency diagnosis, full individual menus, microbial food-safety prediction, pathogen confirmation and complete closed-loop life support are outside the implemented scope. Stored-food expiry and nutrient half lives are user-declared assumptions. Defaults remain labelled synthetic unless explicitly replaced; provenance does not mean every model coefficient has been measured or transferred successfully to this tray.

**The active stack** is React/Vite/Recharts, Python/FastAPI/Uvicorn, Pyomo/HiGHS, ONNX Runtime with the MobileNetV3 classifier, local SQLite for planning/logs, PyMongo/MongoDB Atlas for current telemetry, and Arduino/PlatformIO for the new ESP32 HTTPS uploader. Mosquitto/Node-RED/ESPHome form the earlier optional path. The application no longer uses Streamlit. Reused sources and licenses are recorded in `UPSTREAM_SOURCES.json` and `THIRD_PARTY_NOTICES.md`; Grocy/Mealie remain references rather than integrated features.

**Verification should be described by scope.** The latest affected backend run passed 86 tests for MongoDB, gateway/configuration and API behavior. The latest frontend work reports 44 passed tests and a production build. Earlier model/product work reports 193 Python tests and 13 subtests, with one Windows symlink test skipped; those historical counts are not added together or presented as a newly rerun complete suite. Browser checks cover representative desktop/mobile workflows. Live Atlas evidence is separate from mocked storage tests; compiled firmware is separate from flashed hardware; source-data ML metrics are separate from biological validation.
